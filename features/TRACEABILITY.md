# Capability coverage and migration ledger

This ledger replaces active-spec-only coverage claims. Baseline: commit `3c2f618`, 15 files,
112 scenario declarations and 273 expanded examples. Each declaration, including all its outline rows,
has a disposition below. A link to a test identifies its evidence boundary, not a claim that all previous
prose is proven. Where only part of a scenario is covered, the remaining obligation is explicitly linked.

## Capability map

| Capability           | Specifications                                      | Runtime evidence                                                                                           |
| -------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Tenant access        | 001 tenant resolution; 005 filesystem configuration | Production HTTP refusal/selection; seeded authenticated browser presentation                               |
| Session lifecycle    | 002 session setup                                   | Production session setup and Redis; focused unit matrices                                                  |
| Authenticated access | 003 OIDC; 004 inactivity                            | HTTP initiation; production guard/activity and Redis; focused browser recovery; separate real-provider E2E |
| Tenant configuration | 001, 004, 005                                       | Production filesystem resolution and configuration parsing; callback policy stamping unit tests            |

Requirement tags are namespaced (`@spec-004-FR-005`). Specifications remain historical design inputs;
capability scenarios describe current promises. Lower-level tests can protect a requirement without a
Gherkin duplicate. Counts are inventory, never proof of implementation, accessibility or compliance.

## Explicit coverage gaps

These desired examples are preserved outside the passing regression suite. They are not waived requirements.
Several former bindings modeled these outcomes themselves; others were undiscovered by normal CI. Runtime
coverage must be added at the stated boundary before closing a gap. Do not restore a test-owned implementation.

### G1

**Policy administration and persistence.** Given a representative authorized for Springfield, a change is
persisted through the real administrative boundary, denied for another tenant, and survives session termination.
Invalid proposals preserve the prior value. Existing sessions retain their stamped duration; new authentications
use the new one. Parsing and callback stamping are covered; authorization and durable administration are not.

### G2

**Durable work and general temporary work.** Create a real saved domain record, expire access, reauthenticate,
and retrieve that record through the application. Session-owned unsaved work must remain cleared. The current
protected practice-note UI proves removal of that fixture only; a Set or Map cannot prove persistence or retrieval.

### G3

**Browser activity and resume matrix.** Exercise real keyboard, pointer, touch, scrolling, passive traffic,
independent sessions, sleep/offline/suspended-tab recovery, and non-inactivity causes. Verify no revival and no
protected interaction before authoritative confirmation. The application guard and renewal tests prove server
semantics, not the operating system or input-event integration. The real two-tab expiration journey remains in E2E.

### G4

**Cancellation and provider outage recovery.** Cancel authentication or make the provider unavailable before/
after discovery; exercise the app-owned keyboard retry path without granting access. Wrong credentials and
successful retry run in E2E; a generic mocked discovery exception only proves failure mapping.

### G5

**Broader accessibility verification.** Exercise offered login-failure recovery controls and each failure class
using keyboard and assistive technology. Current browser evidence covers DOM accessibility, focused inactivity
action, and missing-secret guidance; it does not simulate an actual screen reader. E2E retains the full inactivity
Tab/Shift+Tab/Escape assertions and must report defects rather than relaxing them.

### G6

**Operator configuration failures.** Verify unreadable-file/directory failures and actionable error guidance at
the real HTTP/operator boundary. Parser/filesystem tests cover invalid data and paths without claiming usable UI.

### G7

**Multi-tenant provider and restart composition.** Exercise concurrent tenants using a real provider, broker
selection, changed configuration after process restart, and corrected configuration followed by fresh login.
Current HTTP tests verify redirect destinations; application tests verify concurrent identities; static E2E
covers real authentication for one tenant. These facts do not establish the combined cross-host browser journey.

### G8

**Session restart/outage composition.** Production HTTP now verifies frontend restart continuity, tenant removal and existing-cookie refusal.
Restoring unavailable storage and observing the correct reuse/replacement outcome remains unproven as a
composed journey; independent setup and storage tests do not close that remaining obligation.

### G9

**Remaining HTTP composition.** Exercise raw malformed host requests, supporting-resource persistence effects,
secret exposure across response/log surfaces, reusable-cookie invalid configuration, and replacement-session
login as whole HTTP flows. Unit matrices and narrower HTTP assertions remain; their limited scope is explicit.
