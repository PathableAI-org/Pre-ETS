# Feature Verification Plan: Deterministic Application Bootstrap and Runtime Composition

**Feature specification**: [spec.md](spec.md)

**Delivery issue**: None — explicit maintainer exception authorized 2026-10-24

**Status**: Planned — no execution evidence is recorded by this document

## Authority and scope

This plan covers the direct 2026-10-24 maintainer instruction for deterministic bootstrap, fatal startup handling,
progressive observability, coherent process-wide configuration, explicit readiness, and preserved application
behavior. Current `origin/main` revision `d75c6eac498d6c6c59821e71cef6a74bf5e81ecd` supplies the preserved
PREETS-TENANT-004, PREETS-SECURITY-001, PREETS-SESSION-002, PREETS-SESSION-003, and PREETS-SESSION-006 contracts.
The maintainer explicitly waived the ordinary delivery-issue prerequisite for this cross-cutting refactor.

Observability evidence is entirely manual. Automated evidence is limited to deterministic application outcomes and
composition contracts; it must not inspect logs, spans, metrics, exporters, or telemetry-pipeline internals. This
document plans evidence only and makes no claim that any procedure has run.

## Agent-executable manual feature verification _(mandatory)_

### Purpose

Exercise the real frontend process across successful and failed bootstrap stages, inspect progressive diagnostics and
actual telemetry destinations, and establish the strongest readiness/request-gating guarantee supported by the
Next.js host. This adds lifecycle and operational observations that deterministic automated service tests cannot make.

### Prerequisites

- A clean implementation revision with dependencies installed and repository quality checks complete.
- Synthetic tenant and authentication configuration only; no PHI, real client records, production credentials, or production collector headers.
- The repository's supported Node and pnpm versions.
- Redis and any other required application services, with owned test keys and explicit cleanup.
- The existing `otel-lgtm` Compose profile and an authorized Grafana UI or read-only Grafana MCP connection.
- Two unused local ports when a readiness/request race must be observed through separate process and probe clients.
- A controllable, releasable hold that keeps one required startup resource acquisition pending long enough to probe readiness and a business request before release, without turning that resource into a permanent failure.
- A shell capable of capturing standard error, process exit status, timestamps, and request outcomes without committing raw transcripts.

### Procedure

1. Record the exact Git revision, runtime/tool versions, environment type, synthetic fixture identity, enabled telemetry capabilities, collector address class (not credentials), and deployment host mode. Confirm that no real secrets or PHI are present.
2. Start the existing local observability stack with `docker compose --profile observability up -d otel-lgtm --wait`. Use the configured frontend OTLP endpoint and start required Redis/application dependencies with owned synthetic data.
3. Introduce a controllable, releasable hold that keeps one required asynchronous resource acquisition pending. Start the production application with otherwise valid configuration and every telemetry capability enabled. While that acquisition is still pending, probe readiness and issue a business request. Confirm the application has not declared readiness and the business operation does not execute against the incomplete application. Record whether the listener blocked, rejected, or deferred the early request. Release the hold, then confirm readiness and successful request service occur only after that resource and the other required startup stages have completed. Capture standard error and startup timestamps. This is case 1: successful enabled startup and readiness (V-001, V-008).
4. Inspect the configured destinations for the fully enabled startup: structured application logs, an application startup trace and request trace, and application metrics from the recorded window. Inspect one representative item of each enabled signal for safe attributes and correlation, and retain identifiers rather than full payload dumps. Confirm local logging remains available. This completes case 1 (V-003, V-009).
5. Stop the frontend cleanly. Restart it in separate trials: telemetry intentionally disabled by supported configuration while an endpoint or protocol that would be invalid if selected remains present; telemetry not selected because no endpoint is configured, with a non-selected protocol or related setting that would be invalid if selected; and one capability intentionally disabled while the other configured capabilities remain enabled. Confirm successful readiness, continued local standard-error or console diagnostics, no startup failure from unselected malformed settings, absence of a requirement for each disabled or unselected capability, and successful request handling. For the mixed trial, confirm each enabled capability is available and the disabled capability is not required. This is case 2 (V-003, V-004).
6. Stop the frontend. Remove or invalidate one required process-wide setting such as the tenant configuration directory setting. Start the real process, capture the stage-identifying standard-error diagnostic and exit status, confirm no readiness or request service, and inspect output for sensitive values. This is case 3: configuration-validation failure (V-002, V-009).
7. Restore application configuration and configure an invalid observability setting that enablement and endpoint-selection precedence actually selects for an enabled required capability, so initialization fails rather than merely making later export unreachable. Do not use a setting that precedence leaves unselected. Start the real process, confirm fallback standard-error diagnostics identify the observability stage, confirm application-service acquisition did not begin, and record nonzero termination. This is case 4 (V-002, V-004, V-009).
8. Restore valid enabled observability and run separate trials in which Redis is unavailable on the configured address. Trial A leaves the collector available and lets cleanup and export proceed: inspect standard error and configured telemetry for the application-acquisition failure, confirm readiness was never declared, confirm acquired observability resources receive a cleanup and bounded flush attempt, and record nonzero termination. Trials B, C, and D repeat that acquisition failure while, respectively, diagnostic delivery fails, resource cleanup fails, and telemetry flush or export stalls without completing. For trials B–D, the pass condition is nonzero termination and absence of readiness even when the secondary failure prevents the stage diagnostic, cleanup, or flush from completing. Measure elapsed time from the injected acquisition failure until process exit and confirm it finishes within the finite cleanup and telemetry-delivery bound documented by planning, so a finalizer that blocks indefinitely cannot pass. This is case 5 (V-002, V-003, V-009).
9. Exercise collector unavailability in two trials. Trial A keeps a valid selected endpoint configured and the collector stopped or unreachable from process start, then starts the application. Confirm that unreachability is not treated as an observability initialization failure, readiness is declared, valid requests succeed, and local output records best-effort delivery failure. Trial B restores the collector, completes a healthy telemetry-enabled startup, then stops or isolates only the collector and issues valid application requests. Confirm the process remains healthy and serves them while local output records best-effort delivery failure. This is case 6 (V-005).
10. Repeat the successful startup/readiness observation, including the controlled pending-acquisition probe, in each supported deployment form used for this feature (at minimum the documented local production server). For each form, record whether listener acceptance can be blocked and how the integration prevents a partial runtime from executing business operations. This is case 7 (V-001, V-008).
11. Run isolated production-build trials. Each trial starts from an environment that does not inherit a valid runtime configuration from the earlier cases. Cover, separately: runtime services stopped or unreachable; runtime-only credentials absent; a required runtime-only setting such as the tenant configuration directory absent; and that setting malformed. Confirm each build completes without treating those runtime-only settings as required, without acquiring production resources, and without claiming runtime readiness (V-008).
12. Stop only services started for this procedure, remove owned Redis keys and synthetic temporary configuration, restore controlled failure settings, and confirm no temporary probes, output, credentials, or generated reports remain in the worktree.

### Expected observations

- V-001: Enabled startup exhibits the required stage order. While required acquisition is pending, readiness and business operations stay unavailable. After release, readiness occurs only after full acquisition.
- V-002: Each required failure whose diagnostics can be delivered identifies its stage, remains safely diagnosable, never reaches readiness, and terminates nonzero. When diagnostic delivery, cleanup, or flush stalls or fails during application-acquisition handling, nonzero exit still occurs within the planning-defined bound and readiness is never declared.
- V-003: Bootstrap output exists on standard error before full observability. Each enabled capability yields its actual signal, a validly disabled capability is not required, and local output remains available.
- V-004: Intentional disablement or non-selection starts successfully with local logs, including when unselected endpoint or protocol settings are malformed. One disabled capability does not remove the other enabled capabilities. Invalid selected required observability configuration fails startup.
- V-005: Collector unavailability from process start or after initialization is best-effort. It does not prevent readiness or terminate the application, and local output records the delivery failure.
- V-008: The exercised host's readiness/request-gating behavior is recorded accurately, including the pending-acquisition probe. Each isolated production build completes with services unavailable, credentials absent, and required runtime-only settings absent or malformed.
- V-009: No prohibited sensitive value appears in inspected local or exported diagnostic samples.

### Evidence to retain

- Exact Git revision; date/time window; OS, Node, pnpm, Next.js host mode, and relevant service versions.
- Safe configuration summary listing enabled/disabled capabilities and synthetic fixture names without values that are secret or tenant-sensitive.
- Commands/actions, process exit statuses, readiness timing/order observations, pending-acquisition probe results, fatal-termination elapsed times against the planning-defined bound, request statuses, and cleanup result for each of the seven cases, including case 2's disablement trials, case 5's secondary-failure trials, and the isolated production-build trials.
- Safe standard-error excerpts or summaries identifying the stage without retaining configuration payloads.
- Grafana datasource identifiers, trace IDs, log query window/labels, and metric query names/results sufficient for independent review; do not retain authorization headers or full sensitive payloads.
- A limitation statement for listener control, batching delay, exporter behavior, and any deployment form not exercised.

## Operational observability verification

All observability evaluation is manual and uses the real application process and configured telemetry infrastructure.
The observer will use the existing Grafana/OTLP procedure in `docs/observability.md`, extended by the implementation
plan for logs and metrics. Actual exported Effect logs, traces, and metrics must be found in their configured
destinations for the successful startup/request window. Bootstrap and exporter-failure diagnostics must be inspected
from actual standard error. Disabled telemetry, including malformed settings that precedence does not select and a
single disabled capability beside enabled ones, invalid selected initialization, application acquisition failure,
secondary diagnostic/cleanup/flush failure or stall, collector unavailability from process start, and later
collector unavailability must be exercised as distinct cases. Fatal-termination elapsed time is compared with the
planning-defined bound.

No permanent telemetry test, in-memory exporter assertion, output snapshot, log-text assertion, span/attribute
assertion, metric assertion, or exporter mock is permitted. Temporary probes must be removed before completion.

## Environment and data controls

- Use repository-owned synthetic tenant fixtures and scenario-owned Redis prefixes; never clear shared Redis globally.
- Do not use or retain PHI, production tenant identifiers, real credentials, tokens, cookies, authorization headers, or collector secrets.
- Controlled failures must target owned local services or isolated test endpoints; do not disrupt shared environments.
- Mask or omit endpoint userinfo, header values, configuration contents, and provider data from retained evidence.
- Stop only services started by this procedure and remove owned keys, temporary configuration, logs, probes, and captures.

## Evidence retention and reporting

Implementation execution results belong in the implementation pull request or the plan's designated execution record,
not in this planned specification. The record must identify revision, environment, safe inputs/actions, observation,
pass/fail result, cleanup, and limitations for every case. Summaries may link to access-controlled operational evidence
when raw output cannot be retained safely. Planned commands or static checks must never be reported as executed runtime
or telemetry evidence.

## Limitations and incomplete claims

- Local `otel-lgtm` evidence does not establish behavior for every hosted collector, network, deployment platform, or authorization scheme.
- The application can document but cannot exceed the listener/readiness control provided by its Next.js deployment environment.
- This feature does not establish browser telemetry, backend telemetry, vendor selection, alerting, service-level objectives, or production sampling policy.
- Passing preserved behavior suites does not newly establish Microsoft-provider compatibility or complete session features owned by other delivery work.
- Build success does not establish runtime readiness; simulated composition does not establish real Redis or collector behavior.
