## Executive Summary

The spec and plan are a strong, constitution-aligned initiation slice: tenant-first resolution,
`reuse`/`create` entry mapping to the merged session capability, `openid-client` + PKCE transactions,
secret separation, Keycloak beside Redis, and clear out-of-scope callback boundaries. Product scope
(arrive at the tenant’s provider login page) matches the stated workflow.

Two must-address gaps block safe tasking: (1) failed or non-redirecting `create` paths must not issue
the reusable session cookie, or the next visit becomes `reuse` and can serve landing content in
violation of FR-007; (2) active `001` landing-page contract still describes sessionless Display Name
success and needs explicit superseding language before dual approved artifacts diverge further.
Remaining items are recommendations and one stakeholder question about the intentional
anonymous-session landing bypass after an abandoned IdP redirect.

## Suggested edits (propose only — not applied)

### A. `plan.md` — Request and Rendering Design (E1)

Replace step 4 bullet cluster with language equivalent to:

- On `create`, validate OIDC before treating the visit as successful initiation.
- Attach `pathable-session` **only** if this response is a successful IdP `302` (document) or if adapting a future path that intentionally continues SSR without login (not used for failures).
- Config 403 / `login-unavailable` / tx failure / non-document `401`: **do not** `Set-Cookie` the new session; Redis create row may remain until TTL.
- On `reuse`, keep today’s cookie behavior (no renewal required).

### B. `contracts/oidc-login-initiation.md` — HTTP outcomes (E1)

Add column/note: “Session cookie issued?” → Yes only for `reuse` SSR and `create`+IdP `302`; No for 403-config, login-unavailable, 401-nondoc.

### C. `contracts/oidc-login-initiation.md` or `plan.md` — Supersedes (E2)

> **Supersedes** `specs/001-tenant-resolution/contracts/landing-page.md` Successful visit for Proxy-matched document navigations to `/` when session setup returns `outcome: "create"`: those requests MUST initiate OIDC (or fail per FR-007) and MUST NOT serve tenant application Display Name content first. Landing-page Display Name obligations remain for `outcome: "reuse"` only. Implementation MUST update the 001 landing-page contract in the same delivery slice as Proxy initiation.

### D. `spec.md` Assumptions (P2/P3/P4)

Add bullets for mid-journey non-claim, cost of inaction, and (after answer) abandoned-IdP → landing decision.
